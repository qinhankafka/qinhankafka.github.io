PyTorch 调度器：历史视角下的设计与演变

引言：为什么需要调度器？

当你执行这行代码时：

你有没有想过，这个简单的操作背后，PyTorch 是如何找到正确的实现代码的？

a 和 b 可能是 CPU 张量，也可能是 GPU 张量；可能是 float 类型，也可能是 int 类型；可能是稠密张量，也可能是稀疏张量。每一种组合都可能有不同的优化实现。

调度器（Dispatcher） 就是负责解决这个问题的基础设施：给定一个操作（如 add）和输入参数，它能快速定位到应该执行的具体实现。

理解调度器的历史，有助于理解为什么 PyTorch 的内部架构如此设计，以及为什么某些权衡存在。

第一章：起源——TH 库和 Lua Torch 时代

C 时代的张量库

PyTorch 并不是凭空诞生的。它的祖先是 Lua Torch，一个用 Lua 语言封装的张量库。Lua Torch 的核心是 Th 库（Torch Tensor 库），用 C 语言编写。

用 C 语言实现张量操作有一个根本性的挑战：C 没有泛型。当你需要为 float、double、int32、int64 等不同数据类型实现同一操作时，无法像 C++ 模板那样简单写一次就完事。

当时的解决方案是宏生成：

每个操作（如 add、mul、sigmoid）都会生成 8 个变体：

  • THFloatTensor_add
  • THDoubleTensor_add
  • THIntTensor_add
  • THCharTensor_add
  • …

在 Python 绑定层面，代码使用 switch 语句检查张量类型，然后调用对应的 C 函数：

这种模式在当时工作正常，但存在几个问题：

问题 描述
代码膨胀 每个操作都需要为每种数据类型生成独立函数
维护困难 修改一个操作需要同时修改多个生成的变体
性能瓶颈 Python 层的类型检查和函数调用带来额外开销

第二章：过渡到 C++ 和 A10 的诞生

性能问题

当 Facebook 团队开始改进 PyTorch 时，Python 层的性能问题变得不可接受。Sam Gross 的测量表明，对 Python 的依赖是主要瓶颈——每次操作都需要从 Python 解释器层穿越到 C 库，再返回。

Zachary DeVito 的突破

2015 年左右，Zachary DeVito 提出了一个革命性的想法：用 C++ 重新实现张量库，并让这个库的接口与 Python 的语义保持一致。

他花了两个星期完成了这个项目，这就是后来的 A10 库——ATen 的前身。

这个设计的优势

  1. Python 语义一致性：Python 的 torch.Tensor 本身就是引用传递（对象），而不是值传递。A10 设计保持了这一语义，避免了意外的拷贝。

  2. 模块化 CUDA：CUDA 支持作为独立的动态库存在，虚调用可以无缝桥接 CPU 和 CUDA 实现。

  3. 类型安全：编译时的类型检查减少了运行时错误。

第三章：虚拟分派的问题

虚拟分派模式在初期运行良好，但随着时间推移，问题逐渐暴露。

问题 1：vtable 无法扩展

C++ 的虚函数表（vtable）在类定义时就固定了。如果要添加新操作，必须修改基类，重新编译所有子类。

PyTorch 的操作符数量庞大（数百个），每个都修改基类是不切实际的：

问题 2：多贡献者协作困难

PyTorch 是一个开源项目，全球有数百名贡献者。如果每个新操作都需要修改核心 TensorType 类，并等待所有后端（CPU、CUDA、XLA 等）都实现，会严重拖慢迭代速度。

问题 3：autograd 的特殊要求

PyTorch 的自动求导（autograd）系统需要在操作执行前拦截调用，进行梯度追踪。这意味着 **autograd 本身也是一种”后端”**，需要能够注册自己的处理器。

为什么这样设计？

功能键和后端键是分开的优先级系统：

  1. 先比功能键：Sparse > Dense > Quantized，所以 Sparse 优先被处理
  2. 功能键确定后，再看后端：如果是 Sparse，具体是 SparseCPU 还是 SparseCUDA？
  3. 组合：Sparse + CPU = SparseCPU

这种设计允许：

  • dense + dense → 查找 CPU 实现
  • sparse + dense → 查找 SparseCPU 实现（功能键更优先）
  • dense + dense (on CUDA) → 查找 CUDA 实现

分派表查找的 fallback 机制

如果某个操作符在特定 DispatchKey 上没有注册专门的 kernel，调度器会依次尝试以下策略：

四层 fallback 策略
优先级 来源 触发条件 示例
1. 注册 kernel m.impl("add", torch::kCUDA, ...) 操作符为特定 key 注册了 kernel add.CUDA 实现
2. Catch-all kernel m.impl("add", ...) (无 key) 没有为当前 key 注册，但有默认实现 add 的通用实现
3. Backend fallback dispatcher.registerFallback(...) 整个后端没有实现 XLA 后端没有 mm 实现
4. Missing kernel N/A 上述都不存在 报错：”没有 kernel”
Backend Fallback 的用途

Backend fallback 是调度器为整个后端设置的兜底 kernel。主要用途：

  1. 跨设备兼容性：如果某个操作在 XLA 上没有专门实现，可以 fallback 到 CPU 实现
  2. 开发阶段：新后端在开发中时，可以先用 fallback 提供基本功能
  3. 移动端优化：在移动端，fallback 可以提供轻量级的通用实现

Catch-all Kernel vs Backend Fallback

两者都是”找不到专门实现时的兜底”，但范围不同：

  • Catch-all kernel：属于特定操作符的默认实现
  • Backend fallback：属于整个后端的兜底实现，作用于所有在该后端上调用的操作符

第七章：历史约束与设计权衡

CPU 和 CUDA 分离到不同库

由于历史原因，CPU 和 CUDA 实现分布在不同的动态库中：

调度器的设计必须能够跨越这些库边界进行调用。虚拟分派天然支持这一点（虚函数表在运行时解析），而现代调度器通过 DispatchKey 机制实现了类似的功能。

开放注册的需求

用户，尤其是 Facebook 的内部团队，需要能够注册自定义操作符。这些操作符可能不被任何”官方”后端支持，但仍然需要能够参与调度。

调度器的设计允许：

  1. 注册新的 kernel 实现
  2. 覆盖现有的 kernel 实现
  3. 为特定的 BackendComponent 注册 fallback

性能 vs 可扩展性

现代调度器比 vtable 模式慢，但换取了更好的可扩展性和灵活性。这是刻意的权衡：

权衡 vtable 模式 调度器模式
单一操作调用性能 更快（虚函数调用） 稍慢（查找 + 函数指针）
可扩展性 差（需要修改基类） 好（独立注册）
多重分派 不支持 支持
动态加载 困难 容易

README.md 中明确说明了设计目标：

This folder contains the c10 dispatcher. This dispatcher is a single point through which we are planning to route all kernel calls. Existing dispatch mechanisms from legacy PyTorch or caffe2 are planned to be replaced.

总结：理解调度器的演进

PyTorch 调度器的历史，反映了深度学习框架从研究原型到生产系统的演进：

阶段 技术 局限
TH 库 C + 宏生成 无泛型，代码膨胀
A10/ATen C++ 虚函数分派 vtable 难以扩展
现代调度器 自研分派机制 + DispatchKey 性能略低于虚调用，但灵活性大增

理解这些历史约束，有助于理解为什么 PyTorch 的代码库如此复杂，以及为什么某些设计决策是必要的。

当你下次调用 torch.add(a, b) 时，可以想象背后发生的故事：一个从 Lua Torch 的 C 代码演进而来的系统，经过 A10 的虚函数分派，最终演变为今天这个精密的调度机制——它在每次调用时动态决定应该执行哪一段代码，以支持从 CPU 到 GPU、从稠密到稀疏、从普通操作到自定义操作的广泛场景。
