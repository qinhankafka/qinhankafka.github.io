PyTorch 的“消失”术：Variable 的前世今生

如果你是一位经验丰富的 PyTorch 用户，你可能会隐约记得一个叫做 Variable 的类。但如果你是近几年才开始接触 PyTorch，你可能从未在代码中见过它。Variable 曾是 PyTorch 自动求导机制的核心，但如今它已悄然从 Python 前端消失。那么，Variable 究竟是什么？它为何出现，又为何消失？它的“幽灵”又以何种形式影响着今天的 PyTorch？

本文深入探讨了这段有趣的技术演进史，理解它不仅能满足我们的好奇心，更能帮助我们洞察 PyTorch 框架设计的底层逻辑。

一、混沌初开：从 Lua Torch 到 ATen

故事要从 PyTorch 的前身——Lua Torch 时代说起。那时，张量（Tensor）在底层是由 C 语言的结构体（struct）实现的。为了支持不同的数据类型（如 float, double, int），Lua Torch 的底层库 TH 为每一种数据类型都定义了一个独立的 C 结构体，例如 THFloatTensor, THDoubleTensor 等。这种设计使得编写能够通用处理不同数据类型的代码变得异常困难，开发者不得不依赖大量的宏和预处理器来为每种类型生成重复的代码。

随后，PyTorch 诞生了。在早期，它依然沿用了 TH 库的张量实现。直到 Zach（译注：Zachary DeVito）开发了新的 C++ 库 ATen (A Tensor library)，情况才有了改变。ATen 的核心思想之一，就是创建一个统一的、不依赖于具体数据类型（dtype）的 Tensor 类。开发者不再需要为每种 dtype 编写模板代码，这极大地简化了 C++ 层的算子开发，并改善了因 C++ 模板实例化而产生的臭名昭著的编译错误信息。

然而，无论是旧的 TH 库还是新的 ATen 库，它们都只关心张量的数学运算，对自动微分（Autograd）一无所知。

二、Variable 的诞生：为自动求导而生的“包装盒”

在早期 PyTorch 中，自动求导功能完全是在 Python 层实现的。当 Sam（译注：Sam Gross）着手将自动求导功能用 C++ 重写以提升性能时，他面临一个架构上的选择。当时最直接、最简单的方案是维持 ATen 库的独立性，即让张量系统继续对自动求导“一无所知”。

想象一下，你有一个只懂得做数学计算的 Tensor 对象库。现在，你希望为它增加追踪计算历史、构建计算图以便反向传播的功能。如果你不能直接修改 Tensor 的内部结构，你会怎么做？

答案是：给它套上一个“包装盒”。

这个包装盒就是 Variable。Variable 本质上是一个包裹着 Tensor 的容器，它额外存储了自动求导所需的元数据，比如指向创建它的操作的 grad_fn（梯度函数）和用于累积梯度的 .grad 属性。Tensor 负责存储和计算数据，而 Variable 则负责构建和维护计算图。这种分离在当时是一种清晰且易于实现的架构。

三、用户的困惑：Tensor 与 Variable 的“分裂”

这个设计虽然在内部实现上很优雅，却给用户带来了巨大的困惑。社区里充斥着各种各样的问题：

  • “我应该什么时候用 Tensor，什么时候用 Variable？”
  • “Tensor 和 Variable 到底有什么区别？”
  • “什么时候需要用 .data 属性来获取底层的 Tensor？”

对于用户来说，他们脑海中只有三种状态：

  1. 一个需要计算梯度的张量（Variable with requires_grad=True）
  2. 一个不需要计算梯度的张量（Variable with requires_grad=False）
  3. 一个纯粹的 Tensor 对象

问题在于，后两种状态在语义上几乎完全相同，它们都不参与梯度计算。但因为 API 的分裂，用户必须时刻关心自己手中的对象到底是 Tensor 还是 Variable，这增加了不必要的心智负担。

四、历史性的合并：Tensor 吞并 Variable

为了解决用户的困惑，PyTorch 团队在 0.4 版本中做出了一个里程碑式的决定：合并 Tensor 和 Variable。

这个合并过程分两步走，充满了智慧（甚至有点“欺骗性”）：

第一步：前端“障眼法”

在 Python API 层面，团队并没有立刻重构所有 C++ 底层代码。他们走了一条捷径：让 Python 中的 torch.Tensor 类直接变成之前的 Variable 类。也就是说，用户在 Python 中创建的每一个 Tensor，其背后实际上都是那个可以追踪梯度的 Variable 对象。这样一来，Variable 类就从用户的视野中消失了，实现了 API 的统一，但底层的分离依然存在。

第二步：后端“手术刀”——分发器与线程本地状态

前端的统一带来了新的后端挑战。以前，当一个 Variable 上的操作被调用时（如 add），它会先设置好计算图，然后“解包”（unwrap）出内部的 Tensor，再调用 ATen 库中真正的 add 实现。现在 Tensor 和 Variable 合并了，如何区分一个 add 调用是需要构建计算图的“外层调用”，还是一个在算子实现内部、不需要重复追踪梯度的“内层调用”呢？直接调用自己会造成无限递归。

这个难题最终由 Will Feng 通过引入分发器（Dispatcher）和线程本地状态（Thread Local State）解决。让我们来看看当前 PyTorch 2.12 中的实现：

2. 如何避免无限递归

当一个需要求导的 Tensor 调用一个操作时，分发器会先将其导向自动求导的逻辑。在执行完这部分逻辑（例如记录操作到计算图中）后，系统会通过 ExcludeDispatchKeyGuard 设置一个线程本地的排除标志：

然后，它再次调用同一个操作。但这次因为 Autograd 键已被排除，分发器会将其直接导向底层的 ATen 内核实现，从而避免了无限递归。

五、如今与未来：Variable 的幽灵

Variable 在 C++ 中的现状

经过后续的代码重构，Variable 类最终从 C++ 代码库中被彻底清除。今天的 PyTorch 中：

variable.h:25-32

也就是说，在 C++ 层，Variable 现在只是 at::Tensor 的别名，完全没有特殊性可言。

AutogradMeta：存储自动求导元数据的“插槽”

虽然 Variable 消失了，但自动求导的元数据仍然需要存储。今天的 PyTorch 使用了一种更优雅的设计：在 TensorImpl 中预留了一个“插槽”。

c10/core/TensorImpl.h:2920

AutogradMeta 结构存储了所有自动求导所需的信息：

variable.h:227-358

关键设计：只有当 requires_grad=True 时，这个插槽才会被填充并分配内存。这意味着在不需要求导的推理场景（Inference Mode）下，autograd_meta 指针为空，完全没有任何额外开销。

惰性分配：按需填充的插槽

这种设计在性能和安全之间取得了完美平衡：

  • 推理时：零开销，没有梯度相关的数据结构被创建
  • 训练时：按需分配，只为需要梯度的张量创建元数据

六、历史在轮回？

有趣的是，历史似乎在轮回。为了实现更高级的自动微分功能，比如像 JAX 框架那样进行函数变换和嵌套求导，社区正在探索新的实现方式。其中一个原型方案，恰恰是再次使用了“包装”的思想——通过多层包装 Tensor 来追踪不同阶的梯度信息。

Variable 的故事，是 PyTorch 从一个研究工具演变为成熟工业级框架的缩影。它告诉我们，一个优秀的框架不仅需要强大的功能，更需要不断打磨，为用户提供简洁、直观、符合心智模型的编程体验。

而它在 C++ 层面留下的“插槽”设计——用unique_ptr按需分配 AutogradMeta——更是一个经典的设计模式：在不破坏现有接口的情况下，通过预留扩展点来实现功能的演进。

总结

阶段 架构特点 用户体验
Lua Torch 时代 TH 库，每种 dtype 独立结构体 难以编写通用代码
早期 PyTorch ATen 统一 Tensor + Python 层 Variable Tensor 和 Variable 分裂
PyTorch 0.4 Python API 统一，底层通过 Dispatcher + TLS 避免递归 简洁的单一 API
PyTorch 2.12 Variable = Tensor，AutogradMeta 按需分配 高效且统一

Variable 的“消失”并非简单的删除，而是一次精心设计的架构演进：它让复杂的自动求导机制在用户面前消失，却又在底层以更优雅的方式继续存在。
