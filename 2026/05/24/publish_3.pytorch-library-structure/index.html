PyTorch 内部库结构：为什么需要这么多动态库？

PyTorch 似乎是一个单一、整体的库。但在这句简单的命令背后，PyTorch 的内部世界远比表面看起来要复杂。

如果你尝试为 PyTorch 贡献代码，可能会发现一个让人困惑的现象：源码中有 aten、c10、libtorch、torch_python 等众多库——光是搞清楚它们之间的关系，就让人头晕不已。

为什么要这样设计？

原则一：隔离主要依赖项

核心思想

为每一个大型、可选的外部依赖创建一个独立的库，使 PyTorch 可以根据不同使用环境灵活地”穿上”或”脱下”某些重型功能。

CUDA 依赖的隔离

CUDA 是一个庞大的依赖项，与 NVIDIA GPU 硬件深度绑定。但并非所有用户都拥有或需要 GPU。

PyTorch 通过将代码拆分为 aten_cpu 和 aten_cuda 两个库来实现这一点：

BUILD.bazel:231-264

BUILD.bazel:419-457

当用户安装纯 CPU 版本时，构建系统可以完全跳过 aten_cuda 及其所有依赖。

USE_CUDA=OFF 禁用 CUDA，不编译 GPU 相关代码
USE_XPU=OFF 禁用 Intel XPU
USE_ROCM=OFF 禁用 AMD ROCm
USE_CUDNN=OFF 禁用 cuDNN

Python 依赖的隔离

PyTorch 的核心是 C++，但前端是 Python。有些场景需要纯 C++ 环境（服务器部署、嵌入式设备）。

torch/CMakeLists.txt:317-345

这样 C++ 应用程序可以只链接 libtorch，创建不依赖 Python 解释器的独立程序。

原则二：按需使用，优化二进制大小

核心思想

将不同层次的功能拆分开，让用户只链接他们需要的部分。

ATen vs. libtorch：基础计算与神经网络的分离

ATen (A Tensor Library) 提供张量数学运算（加法、乘法等），但不关心神经网络或自动求导。

libtorch 在 ATen 之上构建，包含自动求导引擎、nn::Module 等功能。

aten/src/ATen/CMakeLists.txt:960-963

如果你只需要张量计算，可以只依赖 ATen，避免链接庞大的自动求导和神经网络代码。

ATen/core vs. ATen：移动端最小核心集

项目早期，为了将 PyTorch 移植到移动端，需要一个功能极简、体积超小的核心库。

BUILD.bazel:99-155

ATen/core 只包含移动端场景所必需的最核心功能。

原则三：应对棘手的技术限制

Windows DLL 的 65k 符号限制

在 Windows 上，一个 DLL 最多只能导出约 65,000 个公共符号。

torch/headeronly/macros/Export.h:90-143

Windows 上，C10_EXPORT 和 C10_IMPORT 分别是 __declspec(dllexport) 和 __declspec(dllimport)。

通过将代码分散到多个库中，确保每个 DLL 都符合 Windows 的限制。可以说，在 Windows 平台上，如果不拆分库，PyTorch 将无法发布。

移动端选择性编译

移动应用对体积极为敏感。一个模型可能只用到了 PyTorch 数百个算子中的十几个。

CMakeLists.txt:689-722

cmake/Codegen.cmake:175-207

通过 SELECTED_OP_LIST，移动端构建系统只编译和打包用到的算子。

实例：构建轻量级工业相机应用

假设一家公司想开发一个用于工业相机的 C++ 应用：只在 CPU 上对图像进行预处理，然后发送出去。

通过只链接需要的库，最终可以得到一个非常小巧、高效、无外部依赖的 C++ 程序。

总结

PyTorch 精心设计的库结构是跨越服务器、桌面、移动端和嵌入式设备的关键：

原则 目标
隔离依赖项 灵活配置 GPU、Python 等可选依赖
按需使用 只链接需要的功能，控制二进制大小
技术限制 解决 Windows DLL 符号限制等问题

这些设计在可维护性、性能和部署灵活性之间取得了精妙的平衡。下次当你在 PyTorch 源码中看到这些分离的库时，记住——这正是这个强大框架设计哲学的体现。
