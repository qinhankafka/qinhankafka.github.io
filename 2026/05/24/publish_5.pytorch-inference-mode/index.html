PyTorch 推理模式（Inference Mode）深度解析

引言：为什么需要推理模式？

torch.no_grad() 已经能禁用梯度计算，为什么还需要 torch.inference_mode()？

答案是：即使在 no_grad() 模式下，PyTorch 仍然在后台执行两项无法关闭的额外工作。这些工作是为自动求导准备的，但在纯推理场景下完全多余。

推理模式通过与用户达成”这些张量永远不会用于求导”的约定，大胆地跳过这些开销，同时建立严格的安全检查机制。

版本计数器：自动求导的安全网

为什么需要版本计数器？

反向传播时，自动求导引擎需要用到前向传播时保存的张量原始值。如果在 backward() 调用前张量被原地修改，计算出的梯度就是错误的。

为了检测这种”原地修改”，PyTorch 为每个张量关联了版本计数器：

c10/core/TensorImpl.h:329-350

版本计数器：检测”中间状态被破坏”

一个具体场景

为什么需要检测原地修改？考虑这个例子：

正确的梯度：$b = a^2$，$\frac{db}{da} = 2a$，在 $a=2$ 时，梯度应该是 $4$

如果用修改后的 a：在 $a=3$ 时，梯度是 $6$，这是错误的答案

版本号共享：视图的特殊性

c10/core/TensorImpl.h:307-328

视图共享版本计数器：视图和基张量共享同一个版本计数器。这样对基张量的原地修改也会被视图检测到。

版本计数器的开销

开销 说明
内存 每个张量需要 intrusive_ptr<VersionCounter>
计算 每次原地修改需要 atomic::operator++（原子操作，比普通 ++ 慢）

版本计数器不能防止什么？

  • set_data() 不会增加版本号（故意设计，允许替换底层数据）
  • x.data 也不共享版本号

这些操作会直接替换数据而非原地修改。

推理模式的核心实现

DispatchKey 优先级体系

PyTorch 的 dispatch 是基于优先级的查找：调度时按 enum 顺序从高到低查找，直到找到注册的 kernel。

c10/core/DispatchKey.h:269-344

ADInplaceOrView 的位置：位于功能性 key 和 autograd key 之间。

Dispatch 查找流程

当调用 tensor.add_(1) 时：

  1. 提取 keyset：从 tensor 提取所有 dispatch keys（可能包含 ADInplaceOrView）
  2. 找最高优先级 key：highestPriorityTypeId() 选出 enum 值最高的 key
  3. 查表：在操作符的 dispatch table 中查找对应 kernel

Fallthrough 机制

大多数操作不注册 ADInplaceOrView 的特定 kernel，此时会”穿透”到下一个 key：

aten/src/ATen/core/VariableFallbackKernel.cpp:102-105

只有 inplace/view ops 注册特定 kernel：

  • Inplace ops（如 add_）：注册 kernel 做 version bump
  • View ops（如 view）：注册 kernel 做 DifferentiableViewMeta setup
  • 其他 ops：默认 fallthrough，穿透到 Autograd 或 backend

为什么 InferenceMode 要移除 ADInplaceOrView？

移除后，推理张量的 keyset 中没有 ADInplaceOrView，dispatch 时会跳过这个 key。

但更重要的是：InferenceMode 同时把 autograd keys 加到了 excluded set：

c10/core/InferenceMode.h:64-66

所以 dispatch 查找时：

  1. ADInplaceOrView 不在 included set → 被跳过
  2. Autograd keys 在 excluded set → 被排除
  3. 最终查到 Backend fallback（如 CPU、CUDA）

但因为推理张量本来就不需要 autograd，所以：

  • 跳过 ADInplaceOrView → 不做 version bump → 节省原子操作
  • 跳过 ADInplaceOrView → 不做 view setup → 节省元数据

视图追踪：”梯度感染”问题

视图追踪的场景

如果基础张量 A 不需要梯度，但视图 B 被需要梯度的张量 C 原地修改——“梯度需求”会通过视图”感染”到基础张量 A。

CreationMeta 机制

torch/csrc/autograd/variable.h:690-714

推理模式下创建的视图标记为 INFERENCE_MODE，这个标记会传播，且无法被”降级”。

安全检查：两层保护

第一层：禁止保存推理张量

torch/csrc/autograd/saved_variable.cpp:40-46

如果试图将推理张量保存用于反向传播，立刻报错。

第二层：禁止跨模式原地修改

在推理模式下创建的视图，如果在推理模式外被需要梯度的张量原地修改，立刻报错。

总结

推理模式通过三层机制实现”更快+更安全”：

机制 效果
移除 ADInplaceOrView key 跳过 autograd dispatch
禁用版本计数器 节省内存，避免原子操作开销
CreationMeta 追踪 检测”梯度感染”场景

两层安全检查：

检查 触发条件 结果
SavedVariable guard 尝试保存推理张量 立刻报错
跨模式修改检测 推理视图在模式外被修改 立刻报错

推理模式不是盲目相信用户承诺，而是通过编译器和运行时的严格检查，确保任何违规行为都会被及时发现。
