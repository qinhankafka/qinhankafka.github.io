引言：Python 的温柔与 C++ 的冷酷

等等，Python 世界和 C++ 世界？

在继续之前，我们需要先理解一个问题：为什么 PyTorch 的底层要用 C++？

Python 是一门解释型语言，它的”温柔”在于语法简洁、使用方便。但这种温柔是有代价的——每次执行一行代码，Python 都要”问”解释器：”这一步该做什么？”这种运行时解析带来了巨大的性能开销。

而 C++ 是一门编译型语言，代码在运行前就已经被翻译成机器能直接执行的指令，没有中间商赚差价。

对于深度学习中的矩阵运算这种”简单粗暴”的计算密集型任务，Python 的灵活性反而成了负担。

具体来说：

当你执行 t + 1 时：

PyTorch 需要：

  1. 检查 t 的形状、数据类型
  2. 分配一块新的内存来存储结果
  3. 遍历每个元素，做加法
  4. 把结果写回内存

这些操作对 CPU 来说就是”机械劳动”，Python 的灵活性在这里毫无用武之地，反而拖慢了速度。所以 PyTorch 选择用 C++ 实现这些核心计算，把 Python 作为”前端”来提供友好的接口。

当 C++ 的结果需要回到 Python

现在问题来了：你的代码运行在 Python 世界里，而计算发生在 C++ 世界里。当你执行 t = torch.tensor([1.0, 2.0, 3.0]) 时：

  1. Python 接收到你的请求
  2. Python 调用 C++ 代码创建了一个 Tensor
  3. C++ 代码执行完毕，返回一个结果
  4. 这个结果是一个 C++ 的对象，但你的 Python 代码需要的是一个 Python 对象

在 C++ 世界里，一个 Tensor 就是一个结构体：

但在 Python 世界里，任何东西都是对象，而对象需要一个”头部”来存储类型信息和引用计数。

当你调用 torch.tensor([1.0, 2.0, 3.0]) 时，PyTorch 不能简单地把 C++ 的 TensorImpl 指针直接扔给你。它需要：

  1. 先创建一个合法的 Python 对象（带 PyObject_HEAD）
  2. 把 C++ 的 Tensor 塞到这个 Python 对象里

核心问题：什么时候会多次传递同一个 Tensor？

你可能会问：C++ 的 Tensor 什么时候会”多次”传递给 Python？为什么要强调”同一个”Python 对象？

让我们看一个具体场景：

在这个过程中：

  1. t 被传递到 C++ 的 autograd 引擎
  2. autograd 在 C++ 中执行完反向传播，计算出梯度
  3. 结果需要”放回”到 Python 的 t 对象中
  4. 此时应该返回同一个 Python 对象，而不是创建一个新的

如果每次都创建新对象，会有两个严重问题：

问题 1：对象身份丢失

对于同一个底层 C++ Tensor，如果你多次获取，应该始终返回同一个 Python 对象，这样才能用 t1 is t2 判断它们是否指向同一个底层数据。

问题 2：用户附加属性丢失

总结

所以 PyTorch 需要解决的核心问题是：如何让同一个 C++ Tensor，多次传递给 Python 时，始终返回同一个 Python 对象？

这样才能保证：

  • 对象身份一致：t is t2 能正确判断
  • 用户属性保留：附加在 Python 对象上的数据不会丢失

什么是 THPVariable？

在深入技术细节之前，我们需要先认识一个关键概念：THPVariable。

如果你是 PyTorch 的老用户，可能见过这个名字，但不一定知道它代表什么。

THP 是 Torch Hybrid Python 的缩写——这本身就暗示了它的角色：它是连接”Python 端”和”C++ 端”的桥梁。

字母 含义
T Torch - 来自 PyTorch 的祖先进化
H Hybrid - 混合架构的绑定层
P Python - Python 世界的对象

这要从 PyTorch 的历史说起。PyTorch 最早是从 Lua 语言的 Torch 库发展而来的。当团队决定用 C++ 重写核心代码后，他们需要一种方式让 Python 能够访问这些 C++ 对象。于是产生了 THP——“Torch Hybrid Python”。

在源码中，你能看到这样的定义：

THPVariable 是 Python 端”看到的”Tensor 对象。它包含了 Python 对象必需的 header（PyObject_HEAD），以及指向实际 C++ Tensor 的指针（cdata）。

注意：这里使用的是 at::Tensor（ATen 库中的类型），而不是简单的 Tensor。ATen 是 PyTorch 的 C++ 张量计算库，所有 Python API 最终都会调用 ATen 来执行实际计算。

简单来说：

  • Python 看到的是 THPVariable
  • C++ 实际存储的是 at::Tensor
  • 两者通过 cdata 字段连接

核心问题：复用而非重建

如果我们每次都创建新的 Python 对象，会带来两个问题：

  1. 性能开销：创建对象的成本不可忽视
  2. 对象身份丢失：用户附加的自定义属性会丢失，id(t) 也会变化

PyTorch 解决这个问题的思路是：不要每次都重建，而是复用已创建的 Python 对象。

直接字段存储 vs 哈希表

如果你用过 pybind11，可能会知道它如何处理对象绑定：维护一个全局哈希表，记录每个 C++ 对象和对应的 Python 对象。下次需要传递同一个 C++ 对象时，查表返回已有的 Python 对象。

这听起来很合理，但 PyTorch 的开发者们认为：哈希表的开销不值得。

一个更高效的方案是：与其用哈希表，不如在 C++ 对象上直接放一个字段，记录对应的 Python 对象。

双向强引用与循环引用管理

这里存在一个双向关系：

  • Python 对象持有 C++ Tensor（通过 cdata 字段）
  • C++ Tensor 持有 Python 对象（通过 pyobj_slot_ 字段）

这种双向强引用如果处理不当，容易形成循环引用，导致内存永远无法释放。但 PyTorch 通过主动管理来避免这个问题。

当 Python 对象被垃圾回收时，会执行一个清理过程：

关键变化：

  1. 先清理 hooks：后向传播相关的 hooks 需要先清理
  2. 竞态条件处理：只有当 pyobj_slot 仍然指向当前对象时才清理（可能存在多线程竞态）
  3. 引用计数断言：通过 TORCH_INTERNAL_ASSERT 验证此时没有其他引用
  4. GIL 释放：对于大型 tensor 的释放操作，会临时释放 GIL 以避免阻塞主线程

所以循环引用是被刻意打破的，不是”意外没处理”。

绑定过程：THPVariable_WrapWithType

当 C++ Tensor 需要传递给 Python 时，PyTorch 执行的是 THPVariable_WrapWithType 函数。这个函数是整个绑定机制的核心。

函数概述

这是一个模板函数，可以接受 Tensor&（左值）或 Tensor&&（右值引用）。它的目的是：把 C++ 的 Tensor 变成 Python 对象返回。

返回值是 PyObject*，这是 Python 对象的通用类型。

第一步：获取 PyObjectSlot

还记得之前说的 pyobj_slot_ 字段吗？这里就是获取它。

tensor_impl 是 C++ Tensor 的内部结构，pyobj_slot 是专门用来存储”对应的 Python 对象”的字段。

第二步：检查缓存（核心逻辑）

这是最关键的一行。

load_pyobj() 读取 pyobj_slot_ 字段，看它是否已经指向了一个 Python 对象。

  • 如果有缓存（obj 非空）：直接返回这个对象，增加引用计数
  • 如果没有缓存：需要创建新对象

为什么要用”有缓存就复用”？

  1. 性能好——不需要每次都创建新对象
  2. 对象身份一致——多次获取返回同一个 Python 对象

第三步：创建新对象

当没有缓存时，需要创建新的 Python 对象来包装 C++ Tensor。这一步分为多步：

3.1 tp_alloc 分配原始内存

type->tp_alloc(type, 0) 是 Python 的对象分配函数。它分配一块原始内存，但不调用任何构造函数。

3.2 PyUnstable_EnableTryIncRef

这是一个针对自由线程 Python（free-threaded Python，即无 GIL 的 Python）的兼容性处理。在 Python 3.13+ 引入了自由线程模式，多个线程可以同时执行 Python 代码。PyUnstable_EnableTryIncRef 允许对象在这种环境下正确处理引用计数。

3.3 reinterpret_cast 类型重解释

reinterpret_cast<THPVariable*>(obj) 告诉编译器：”把这块内存当成 THPVariable* 来用”。

3.4 placement new 构造对象

这是 placement new（定位 new），不是普通的 new。

普通 new：分配内存 + 调用构造函数

placement new：只在指定地址调用构造函数

这里为什么需要 placement new？因为 tp_alloc 分配的内存不属于 C++ 的堆，用普通 new 无法正确构造对象。placement new 允许我们在任意内存地址上构造对象。

第四步：选择初始化路径

创建完新对象后，需要把 C++ Tensor 和 Python 对象绑定起来。但此时可能有线程竞争，所以要根据情况选择不同的绑定策略：

情况 A：快速路径

如果这个 Tensor 只被当前这一个引用持有（is_uniquely_owned() 返回 true），说明绝对不可能有线程竞争，可以直接写入 pyobj_slot_，使用更高效的 non-atomic 操作。

情况 B：普通路径

如果 Tensor 被多个引用持有，可能有多个线程同时尝试绑定。此时：

  1. 用 CAS（原子操作）尝试设置 pyobj_slot_
  2. 如果 CAS 失败（另一个线程抢先了），就放弃自己创建的对象，用那个”已经存在的对象”
  3. return Py_NewRef(wrapper) - 返回另一个线程创建的对象

线程安全：不用 GIL，而用 CAS

你可能会想：Python 不是有 GIL 保护所有对象操作吗？

但问题在于，pyobj_slot 的写入发生在 C++ 层，此时 Python 解释器还没参与进来。GIL 只保护 Python 对象，保护不了 C++ 对象的创建过程。

PyTorch 的解决方案是：CAS（Compare-And-Swap）原子操作。

这确保了即使多线程并发，也只有一个 Python 对象会被绑定到某个 Tensor 上。

生命周期独立性

这里有一个重要的问题值得思考：

如果 Python 对象被释放，C++ Tensor 也会跟着释放吗？反过来呢？

直觉上，你可能觉得答案是”会”，毕竟它们是”强绑定”的。

但实际情况是：两者的生命周期是独立的。

Python 对象和 C++ 对象各有独立的引用计数系统：

  • Python refcount 控制 THPVariable 的生命周期
  • C++ refcount 控制 TensorImpl 的生命周期

两者通过 pyobj_slot 和 incref/decref 协调，但不存在”生死绑定”的关系：

场景 Python 对象 C++ 对象
删除 Python 变量 t Python ref = 0 → THPVariable 被 GC 回收 C++ ref 可能仍 > 0 → TensorImpl 仍然存活
C++ 引用全部释放 Python ref 仍 = 1 → Python 对象仍存活，但 pyobj_slot 已被清空 C++ ref = 0 → TensorImpl 被释放

这意味着：当你”del t”一个 Tensor 时，C++ 的底层数据可能还活着。

对象身份丢失：一个真实的问题

现在我们来到了一个关键的陷阱。

如果你给一个 Tensor 设置了自定义属性，然后这个 Tensor 的 Python 对象被 GC 回收了，下次你再访问同一个 C++ Tensor 时，会得到一个全新的 Python 对象——它不再是”原来那个”了。

这听起来像个 bug？实际上，这是当前设计的固有特性。

为什么这么说？因为 Python 对象被回收时，pyobj_slot 被清空了。下次再传递这个 Tensor 到 Python 时，PyTorch 认为这是”第一次”，所以创建新对象。

这是一个权衡：

  • 优势：不需要全局哈希表，性能更好
  • 代价：Python 附加属性在某些场景下会丢失

为什么这样设计？

你可能会问：为什么不干脆用哈希表保证同一性？

开发者们权衡了很久：

  1. 性能优先：每次绑定都查哈希表，在高性能场景下是不可接受的
  2. 简单直接：O(1) 字段访问远比哈希表查找快
  3. 历史原因：PyTorch 最早的设计就是为了追求极致性能

所以这是刻意的工程决策，不是疏忽。它在大多数场景下工作得很好，但在某些边界情况下会暴露这个限制。

总结：理解设计权衡

PyTorch 的 Tensor-Python 绑定机制背后，是一系列精心权衡：

设计决策 权衡
直接字段存储 vs 哈希表 性能 vs 全局状态
强引用 vs 弱引用 生命周期管理复杂性 vs 对象身份保持
引用计数协调 同步成本 vs 内存安全

这些决策没有绝对的对错，只有适合与否。PyTorch 选择了一条性能优先的道路，为此在某些边界情况下付出了代价——但对大多数用户来说，这通常是透明的。

理解这些设计背后的思路，能帮助你在遇到”奇怪”的问题时，快速定位根源。毕竟，当你知道规则是什么的时候，例外也就没那么可怕了。
