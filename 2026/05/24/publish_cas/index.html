CAS（Compare-And-Swap）：多线程编程的基石

为什么需要 CAS？

在多线程环境中，多个线程可能同时访问和修改同一个变量。普通的读-改-写操作不是原子的，可能导致严重的问题。

例子：非原子操作的问题

如果两个线程同时进入这个 if 分支：

  1. 线程 A 和 B 都读取到 nullptr
  2. 线程 A 写入 pyobj_A
  3. 线程 B 写入 pyobj_B，覆盖了线程 A 的结果

最终结果：slot 指向 B，但 A 的操作”丢失”了。

CAS 的原理

CAS 的核心思想很简单：**”只有当这个值是我期望的值时，才把它改成新值；否则什么都不做”**。

这类似于乐观锁：先假设没有竞争，试试看，失败了就重来。

关键点：这个操作是原子的，硬件保证在执行过程中不会被其他线程打断。

C++ 中的 std::atomic::compare_exchange_strong

在 C++11 中，CAS 操作封装在 std::atomic 类型里：

参数

  • expected：指向期望值的指针。函数会比较 value 和 *expected
  • desired：要写入的新值

返回值

  • true：交换成功（value 等于原来的 *expected，已设置为 desired）
  • false：交换失败（value 不等于 *expected，*expected 被更新为 value 的当前值）

compare_exchange_strong vs compare_exchange_weak

C++ 提供了两个 CAS 操作：

方法 区别
compare_exchange_strong 保证只有在真正不相等时才返回 false
compare_exchange_weak 可能因为伪失败（spurious failure）返回 false，即使当前值等于 expected

伪失败：在某些硬件实现中，weak 可能无故返回 false，但下次重试可能就成功了。

选择建议：

  • 一般情况下用 strong，更直观
  • weak 在循环中使用更高效（可以配合 while 循环）
  • 在 PyTorch 中，使用的是 strong

CAS 的 ABA 问题

CAS 有一个经典问题：ABA 问题。

场景

  1. 线程 A 读取值 A
  2. 其他线程把值改成 B，再改回 A
  3. 线程 A 用 CAS 检测，发现还是 A，认为没有人动过

但实际上，值已经被修改过了。

解决

用双字或版本号来检测中间变化：

  • 在 PyTorch 的引用计数中，用 combined_refcount 存储更多信息
  • 不仅仅检测指针相等，还检测版本/状态

总结

CAS 是多线程编程中的原子操作基石：

概念 说明
CAS 原子操作：只有当值等于期望时，才写入新值
compare_exchange_strong C++ 中实现 CAS 的方法，失败时明确返回 false
返回 true 交换成功，值已更新
返回 false 交换失败，expected 被更新为当前值
ABA 问题 CAS 的经典陷阱，需要用版本号解决

CAS 让多线程可以在不使用锁的情况下安全地修改共享变量，是高性能并发系统的核心技术。
