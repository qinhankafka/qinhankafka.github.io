深入探索PyTorch的后端可扩展性：从CUDA到XLA的演进之路

引言：什么是后端可扩展性？

在开始之前，我们需要先理解一个问题：为什么 PyTorch 的底层要用 C++？

Python 是一门解释型语言，它的”温柔”在于语法简洁、使用方便。但这种温柔是有代价的——每次执行一行代码，Python 都要”问”解释器：”这一步该做什么？”这种运行时解析带来了巨大的性能开销。

而 C++ 是一门编译型语言，代码在运行前就已经被翻译成机器能直接执行的指令，没有中间商赚差价。

对于深度学习中的矩阵运算这种”简单粗暴”的计算密集型任务，Python 的灵活性反而成了负担。

后端可扩展性的定义

PyTorch 作为一个深度学习框架，其核心使命之一就是提供 GPU 加速。如果没有 GPU 加速，我们或许可以直接使用 NumPy 来完成大部分工作。GPU 加速意味着同样一套 Python 代码，不仅可以在 CPU 上运行，还可以在像 CUDA 这样的强大硬件上运行。

在 PyTorch 的语境中，我们将这些不同的计算平台（如 CPU、NVIDIA GPU、AMD GPU、TPU）称为”后端（Backend）”。

在 PyTorch 项目初期，只有两种官方支持的后端：CPU 和 CUDA。这可以追溯到它的前身 Torch7（以及更早的 LuaTorch）时代，当时主要由 TH（CPU 张量库）和 THC（CUDA 张量库）这两个库主导。

然而，随着时间的推移，越来越多的硬件厂商和研究机构希望将他们自己的硬件或加速器与 PyTorch 集成。这就引出了我们今天的主题——如何让 PyTorch 能够灵活地接入更多、更多样化的后端？

为什么 PrivateUse1/2/3 高于内置后端？

设计意图：

  • PrivateUse1/2/3：供用户自定义后端使用，优先级高意味着用户可以实现自己的后端并覆盖内置后端的默认行为
  • Meta：用于”元张量”（meta tensors），即只有 shape/dtype 信息但没有实际数据的张量。主要用于形状推导和编译时分析，不应该真正执行计算

为什么 Meta 要放在最后？

c10/core/DispatchKey.h:27-30

核心原因：Meta 必须放在最后，以确保显式设置 Meta 时一定能触发 Meta 内核。

关键理解：这里的”最后”是针对后端组件（BackendComponent）的排列顺序，而不是”兜底”或”最后才用”的意思。

  1. Meta 是特殊的后端：它不代表真正的计算硬件，而是用于元张量（meta tensors）——只有 shape/dtype，没有实际数据
  2. 形状推导的场景：当你只需要推导输出形状而不需要真正计算时，会使用 Meta 后端
  3. **Thread Local Storage (TLS)**：当在 TLS 中显式设置了 Meta key 时，需要确保 Meta 内核被触发

二、案例一：与 CUDA”形似”的后端——AMD ROCm

PyTorch 的架构最初是为 CPU 和 CUDA 量身定做的。因此，如果一个新的后端在设计上与 CUDA 非常相似，那么集成过程就会相对顺利。AMD 的 ROCm 平台（及其 HIP 编程语言）就是一个绝佳的例子。

HIP：CUDA 的”表亲”

CUDA 是 NVIDIA 的专有技术，只能运行在 NVIDIA 的 GPU 上。而 AMD 作为另一家主要的 GPU 制造商，也推出了自己的通用计算平台 ROCm。为了快速追赶 NVIDIA 在软件生态上长达十年的领先优势，AMD 采取了一种非常聪明的策略：尽可能地模仿 CUDA。

ROCm 中的 HIP 语言在语法和 API 上与 CUDA 高度相似。这使得 PyTorch 在支持 AMD GPU 时，可以走一条捷径——PyTorch 编写的 CUDA 内核（Kernel），可以通过一个名为 hipify 的脚本，自动地被”转译”成 HIP 内核。

ROCm 的设备检测

aten/src/ATen/DeviceAccelerator.cpp

保持”cuda”名称的”折中”方案

为了最大程度地复用已有的代码和测试（这些代码和测试都是围绕 cuda 这个标识符编写的），AMD 版本的 PyTorch 在用户 API 层面保留了 cuda 的名称。这意味着，当你使用一个为 AMD GPU 特殊编译的 PyTorch 时，你仍然会调用 .cuda() 方法来将张量移动到 AMD 的 GPU 上。

三、案例二：与 CUDA”神异”的后端——Google XLA

并非所有后端都像 ROCm 那样与 CUDA 相似。Google 的 XLA（Accelerated Linear Algebra）就是一个完全不同的例子，它的集成也揭示了 PyTorch 后端扩展的更深层次机制。

XLA 的核心区别：惰性求值 vs 立即求值

注意：PyTorch 2.0 之后，CUDA 也可以通过 torch.compile 使用图模式优化（Dynamo + Inductor）。所以 XLA 和 CUDA 的核心区别不是”能否图模式”，而是求值策略的不同：

特性 CUDA XLA
求值策略 立即执行（Eager） 惰性执行（Lazy）
同步时机 隐式同步，结果立即可见 需要显式同步（如 xm.mark_step()）
内存分配 同步分配，立即知道 shape 延迟分配，shape 通过 build() 推理
图构建方式 Dynamo 捕获 FX 图 XLA 自己维护计算图

惰性求值的实现

关键区别：CUDA 操作执行后会立即同步结果；XLA 操作只是往图中添加节点，真正的计算延迟到同步时刻。

这意味着 XLA 有机会在真正执行前：

  1. 看到完整的计算图
  2. 进行跨节点优化
  3. 融合算子减少内存访问

CPU 回退机制

torch/csrc/lazy/ts_backend/ts_eager_fallback.cpp:197-205

当遇到一个 XLA 本身不支持的 PyTorch 算子时，XLA 后端会执行回退（fallback）操作：

  1. 将相关的张量数据拉回到 CPU
  2. 调用 PyTorch 原生的 CPU 实现来完成计算
  3. 将结果传回 XLA 设备

四、案例三：自定义后端——PrivateUse1 完整指南

PyTorch 提供了三个”私有后端”槽位（PrivateUse1/2/3），允许开发者注册自己的自定义后端。这对于研究性质的后端或者企业内部的后端特别有用。

4.1 为什么需要 PrivateUse1？

c10/core/DispatchKey.h:49-51

这三个后端是完全由用户定义的：

  • PyTorch 核心代码不会为其实现任何算子
  • 用户可以自由地将任何算子注册到这些后端
  • 优先级高于内置后端（除了 Meta）

五、Codegen：胶水代码的自动化生成

5.1 为什么需要 Codegen？

手动为每个后端编写注册代码是极其繁琐的。PyTorch 面临的情况是：

  • 数百个算子
  • 数十个后端
  • 每个算子需要为每个后端提供一个实现

Codegen（代码生成）解决了这个问题：只需编写一次算子定义，自动化生成所有后端的注册代码。

5.2 native_functions.yaml：算子定义

5.3 torchgen：Python 端的 Codegen 模型

torchgen/model.py:100-170

PyTorch 使用 Python 版本的 DispatchKey 枚举来生成 C++ 代码，保持两者同步。

5.4 Codegen 工作流程

关键点：PyTorch 使用 torchgen 将 native_functions.yaml 中的算子定义转换为 C++ 注册代码。每个后端对应一个 RegisterXXX.cpp 文件（如 RegisterCPU.cpp、RegisterCUDA.cpp）。

六、后端扩展的挑战：永不停歇的”跑步机”

为 PyTorch 添加和维护一个外部后端是一项巨大的挑战，就像踏上了一台永不停歇的”跑步机”。

签名变更的破坏性

对于 Python 用户来说，这是一个完全兼容的改动。但对于用 C++ 为后端实现 some_op 的开发者来说，这却是一个破坏性变更，因为他们的函数签名不再匹配，导致编译失败。

CI 集成的重要性

XLA 团队能够成功，很大程度上是因为他们的代码被整合进了 PyTorch 的持续集成（CI）系统中。

八、总结

PyTorch 的后端可扩展性是一个不断演进的故事：

后端类型 代表 集成难度 关键挑战
与 CUDA 相似 AMD ROCm/HIP 低 保持 API 兼容性
与 CUDA 完全不同 Google XLA 高 需要惰性求值和图优化
自定义后端 PrivateUse1/2/3 中 依赖社区支持

核心要点：

  1. Dispatcher 是路由核心：通过 DispatchKey 确定使用哪个后端的实现
  2. 优先级由位置决定：enum 中越靠后的 DispatchKey，优先级越高
  3. Codegen 自动化：native_functions.yaml 定义算子，torchgen 自动生成所有后端的注册代码
  4. PrivateUse1 完整方案：从 C++ 算子注册到 Python 绑定，再到 Inductor 集成
  5. BackendImplInterface 抽象：简化新后端的集成过程

从最初与 CUDA 紧密耦合的架构，到通过 Dispatcher 和动态注册机制支持像 XLA 这样截然不同的后端，PyTorch 正变得越来越开放和灵活。PyTorch 2.12 已支持 MTIA、MAIA 等新后端，并通过 PrivateUse1/2/3 为自定义硬件提供便捷的集成路径，为一个更加多元化的硬件生态系统做好了准备。
